# План обновления UI планшета и прокачки классов

Дата: 2026-09-27. Статус: предложение перед реализацией.

## Границы работы

Сохраняем один JAR, текущую архитектуру мода, экономику и серверные правила. Работа ограничена UI планшета, его ресурсами и локальной оптимизацией. Не переписываем кланы, контракты, голосования и HUD. Существующие class keys, tier IDs и packet IDs сохраняются.

## Что сейчас реализовано

- `TabletScreen` координирует оболочку, страницы, действия, tooltip и диалоги.
- `TabletNavigationRail`, `TabletPageState`, `ScrollableActionGrid`, `TabletDataViewport` и `TabletProfileView` уже отделены и переиспользуются.
- `TabletActionCard` рисует карточку 130×34, включая значок 16×16 и одну строку статуса. Сетка содержит две колонки и четыре видимые строки; область содержимого — 274×150, оболочка — 380×220 GUI units.
- `TabletClientState` получает XP, tier, баланс и ограничения от сервера; `ClassTier` описывает пороги и цены.
- Один клик на карточку выбирает класс, покупает магазинный класс, открывает базовый класс или предлагает повышение. Отмена повышения запоминается в `dismissedUpgradePrompts` и меняет дальнейшее поведение клика.
- XP и цена уже существуют в текстах, но конкурируют с кулдауном, отсутствием матча и другими статусами; постоянной шкалы нет. Текст карточки обрезается до 88/92 GUI units.
- Подтверждение использует общий `TacticalDialog`; для повышения кнопка сейчас называется «ОК». Результат повышения сообщается серверным сообщением, а не отдельным структурированным ответом UI.
- В `TabletScreen` остаются старые классы диалогов без найденных вызовов конструкторов. Удалять только после полной проверки ссылок и тестов.

## Что сохраняем

Аппаратную рамку планшета и варианты оформления по tier, навигацию по категориям, независимое состояние прокрутки, отдельный RTP, keyboard navigation/narration, общий `TacticalDialog`, frame clock, scope для blend/scissor и кэш наличия ресурсов. Ограничения competitive, chaos, VIP и marine остаются серверными и сохраняют текущую семантику.

Документ `tactical-ui-ux-redesign-plan.md` содержит исторические проблемы, часть которых уже устранена. Перед работой ориентируемся на код и актуальный `ui-render-contract.md`, не повторяем законченные миграции.

## Основное решение UX

Разделить использование класса и управление его развитием. Предлагаются два режима внутри страницы классов: «Выбор» и «Прокачка». Это режимы UI, а не новые игровые режимы или отдельная архитектура.

### Выбор

Карточка показывает значок, название, сохранённый tier и состояние использования. Основное действие — «Выбрать»; оно больше не открывает покупку повышения. Для закрытого класса действие явно называется «Открыть — N монет». Покупка магазинного класса сохраняет собственную подпись и подтверждение. Неизменяемые по текущим правилам классы не получают фиктивную шкалу прокачки.

В доступной геометрии проверить карточки примерно 130×46: три видимых ряда вместо четырёх. Это позволяет разместить тонкую шкалу без уменьшения читаемости. Окончательную геометрию выбрать после макета в реальном GUI scale. Если рамка не допускает увеличение высоты, сохраняем компактные карточки выбора, а полный прогресс показываем в режиме «Прокачка».

### Прокачка

Рекомендуется список базовых классов на всю ширину с переходом в подробности выбранного класса внутри той же области планшета. Широкая строка показывает значок, имя, текущий tier, XP, следующий tier и цену. Подробности содержат:

- крупный значок и имя;
- цепочку «Базовый → Редкий → Эпический → Легендарный → Монстр» с отметками текущего и следующего;
- отдельную шкалу текущего этапа и общий XP;
- цену следующего повышения и баланс;
- явную кнопку «Повысить до [tier] — N монет»;
- текст причины недоступности;
- возврат к списку с сохранением scroll/focus.

Не пытаться одновременно уместить каталог и подробности в существующие 274×150. На первом этапе не расширять рамку вслепую. Навигация к прокачке должна быть явно видна на странице выбора; её нельзя прятать только в tooltip.

## Семантика прогресса

XP накопительный, при повышении не расходуется. Заполнение текущего этапа вычисляется как:

`clamp((xp - current.requiredXp) / (next.requiredXp - current.requiredXp), 0, 1)`.

Пример: сохранённый Редкий tier и 650 общего XP означают 350/500 XP текущего этапа, 70%, ещё 150 XP до Эпического. Не показывать 650/800 как заполнение текущего этапа без объяснения.

Текущие пороги и цены из `ClassTier`:

| Повышение | Общий XP | Цена |
|---|---:|---:|
| Базовый → Редкий | 300 | 50 |
| Редкий → Эпический | 800 | 100 |
| Эпический → Легендарный | 1300 | 250 |
| Легендарный → Монстр | 2000 | 500 |

Эти значения не дублировать литералами в UI. Опыт ограничивается cap сохранённого tier: при достижении порога написать «Опыт этого этапа заполнен. Повысите класс, чтобы продолжить накопление». Максимальный tier показывает «Максимальный уровень» без следующей цены.

Состояния отображаются независимо от использования: отсутствие матча, использованный комплект и кулдаун не скрывают прогресс. В competitive UI объясняет запрет покупки повышения; постоянный сохранённый прогресс и фактический tier комплекта режима не смешиваются. Chaos сохраняет свой выбор предложенных классов и не становится магазином повышения.

## Покупка повышения

1. Игрок явно нажимает повышение.
2. Общий диалог показывает класс, текущий/целевой tier, цену, баланс до/после и пояснение «XP не списывается; открывается следующий этап накопления».
3. Кнопки: «Повысить — N монет» и «Отмена». Отмена не меняет доступность дальнейшей прокачки.
4. Непосредственно перед отправкой проверяется актуальное клиентское состояние: класс открыт, следующий tier соответствует текущему, достаточно XP/монет и разрешён режим. Авторитетная проверка остаётся серверной.
5. Отправляется существующий upgrade action; повторная отправка блокируется локальным pending-состоянием, привязанным к class key и target tier.
6. UI не списывает монеты и не увеличивает tier оптимистически. После подтверждённого snapshot отображаются новые данные и краткое уведомление.
7. Таймаут означает «Результат ещё не подтверждён», а не неудачу или успешную покупку. Автоматического повторного платежа нет.

Без изменения протокола можно подтвердить достижение target tier по синхронизированному состоянию, но нельзя точно связать все ошибки с конкретным запросом. Подробный вывод причины отказа внутри планшета требует отдельного обсуждения расширения ответа с request ID и кодом результата. Это отдельный этап; ID существующих пакетов не перенумеровываются, изменение формата требует согласованной версии протокола.

## Анимации

Переиспользовать `AnimatedFloat`, `UiFrameClock`, `TacticalUi` и текущий render contract. Предлагаемые длительности: hover/focus 100–140 ms, переход содержимого 140–180 ms, изменение шкалы 200–300 ms. Это целевые параметры макета, а не измеренная необходимость.

Анимировать только визуальный слой, не hitbox и не значение XP. Новые числа показываются сразу; интерполируется заполнение шкалы. При смене класса не интерполировать шкалу от предыдущего класса. Успех повышения подсвечивать один раз после серверного обновления. Нет постоянного мигания, тряски, частиц и обязательных шейдеров. Reduced motion должен реально передаваться экраном: сейчас `TabletScreen` передаёт `false`. Конкретный источник настройки определить до реализации.

## Локальная оптимизация

- Ввести небольшой неизменяемый client presentation model для класса: ownership, saved tier, XP, next tier/price, separate use/upgrade availability и причины. Это вспомогательный объект текущего UI, не перестройка архитектуры мода.
- Пересчитывать статические тексты/иконки/переносы при изменении соответствующих данных, языка, ресурсов или layout. Кулдаун обновлять отдельно с необходимой частотой; не кешировать доступность навсегда.
- Повторно использовать widgets при обновлении данных; `init()` оставлять для создания/изменения layout.
- Рисовать только видимую часть списка и сохранять текущие blend/scissor scopes.
- Перед удалением legacy dialog-классов проверить все ссылки. Удаление допустимо только в рамках затронутого purchase slice.
- Базовые измерения: одинаковая сцена/GUI scale, открытие и прокрутка планшета, изменение snapshot; сравнить frame time и allocations. Не обещать прирост FPS без измерений.

## Приёмка и проверки

Игрок без tooltip видит свой tier, XP, следующий порог и цену; отдельное действие повышения не меняет выбор комплекта. Цена видна и при недостатке монет. Ready-состояние не означает бесплатное/автоматическое повышение. Отмена не скрывает повышение. Успех появляется после server commit/sync. Прогресс виден вне матча и на кулдауне. Политики режима не меняются.

Regression tests: progress boundaries, maximum, locked, insufficient XP/coins, exact balance, competitive restrictions, separate action semantics и pending snapshot/timeout. Существующие packet/persistence tests сохраняются. Ручная проверка: mouse/Tab/arrows/Enter/Esc, focus после диалога, скролл, GUI scale, длинные RU/EN строки, resource reload/fallback, задержка сети, повторный клик, выход/повторный вход и одиночная игра.

После изменения кода: минимально релевантные tests, затем `./gradlew clean build` и `git diff --check`. Этот документ не утверждает, что UI реализован или игровые проверки уже пройдены.
